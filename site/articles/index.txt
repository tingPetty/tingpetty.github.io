1d:T124b,换个聊天窗口，ai 又忘了昨天改过什么 记忆存在外面的笔记柜里。下次开始工作，究竟先拿哪几张卡片出来？ 技术 ai 项目笔记 “这个方案昨天已经试过了。”

和 ai 一起处理一个稍长的项目，这句话应该不难想象。上次为什么放弃某种做法、某个报错是怎么解决的，换一个会话，又得重新讲一遍。

当然，可以自己写一份项目笔记。但每天读了什么、改了什么、试过什么，靠人手动补记录也挺费劲。

claude-mem 尝试把这件事接过去：从 agent 的工作过程里留下记录，整理成较短的观察和摘要，等下次会话需要时，再取出相关内容。它现在已经提供多种 agent 的适配入口，名字里的 claude 不代表全部使用范围。[项目 readme](https://github.com/thedotmack/claude-mem#readme) 介绍了支持情况。

## 记忆先存在外面

这里说的“记住”，发生在模型外部。

可以想象一个人每天换一张干净的办公桌，但桌边一直放着同一个笔记柜。新的一天开始，先取几张和今天任务有关的卡片，就不必全靠重新回忆。

claude-mem 的基础流程也有类似分工：在工作发生时收集信息，用一个观察过程整理记录，再把结果保存下来。新会话开始时，按项目提供一份紧凑的上下文。这里的“上下文”，就是这次交给 ai 参考的材料。[官方架构说明](https://docs.claude-mem.ai/architecture/overview) 展示了这些部件的关系。

这不会把一个项目的经历直接训练进模型参数。离开这套记录和读取机制，模型也不会凭空拥有同样的项目记忆。

![claude-mem 分成两条路径：工作时整理并保存笔记，新会话按需检索笔记](/media/4507e78098d9544e72c51dcd75105e177a8fcf081e772434218c5153d45e342f.webp)

## 笔记从哪里来

项目通过 hooks 接收 agent 的事件。hook 可以理解成一个预先约定的通知点：开始会话了、调用工具了、结束了，就通知相应的处理程序。

在 `src/cli/hook-command.ts` 里，能看到适配器先把不同平台的输入整理成共同格式，再交给事件处理器，最后把结果转换回平台需要的形式。[对应源码](https://github.com/thedotmack/claude-mem/blob/main/src/cli/hook-command.ts) 还专门处理了失败时怎样退出，尽量避免记笔记的环节把原本的工作卡住。

后面有一个本地 worker，可以把它理解成后台值班的小服务。它接收事件、安排整理、提供搜索和上下文等接口。这个部件的入口是 [`src/services/worker-service.ts`](https://github.com/thedotmack/claude-mem/blob/main/src/services/worker-service.ts)。

记录主要存进 sqlite。sqlite 是一种可以把数据库放在本地文件里的工具。项目把会话、观察记录、摘要等信息分开保存，也保留记录所属项目、发生时间等信息。[数据库文档](https://docs.claude-mem.ai/architecture/database) 可以看到具体组织方式。

## 先翻目录，再抽卡片

如果每次都把过去所有笔记塞给 ai，材料会越来越长。里面还可能混着几周前已经不用的方案。

claude-mem 在 readme 中介绍了一条分步检索路线：先用 `search` 找到简短索引；需要了解前后经过时，再用 `timeline`；最后通过 `get_observations` 取选中的详细记录。

这有点像查一本书：先看目录，翻到那一节，再决定要不要往前多读两页。先给出的信息少一些，后面仍然留着回查详情的入口。

比如，假设记录里有一张卡片写着“菜单故障和某个事件处理有关”。它可以帮我们找到上次调查的位置。但真正要改代码时，仍然应该打开现在的文件，看看相关逻辑有没有被后来的修改替换掉。

记忆可以提供线索，旧结论有没有过期，还得再判断。

## 顺着一条笔记读源码

这次阅读时，我给自己留的路线很短：

`src/cli/` 接收事件 → `src/services/worker/` 处理 → `src/services/sqlite/` 保存 → `src/services/context/` 组织下次要带上的内容。

每经过一处，都可以问同一个问题：“上一环节交过来的内容，在这里变成了什么？”这样比一口气研究所有配置容易跟住。

对我来说，这个项目最有意思的地方是它怎样挑选信息。记下所有东西不难理解，真正影响使用体验的，往往是下次打开聊天时，究竟先拿哪几张卡片出来。

## 一条留言，先变成一张工单

在这个系统里，外部消息进来后，会被记录成事件。系统根据规则判断它是否要求开始一项工作。接下来的解释，先只看“收到一个新任务”这条路径。

通过判断后，系统建立一张 ticket。这个词可以直接理解成工单：这件事要做什么、为什么可以做、结果回到哪里，都需要有地方记下来。

其中还有一个叫 mandate 的记录，用来保存这次工作的授权依据和范围。这里不用背英文，记住一个区别就够了：**知道有人说了什么，和获准替他做什么，是两件不同的事。** 相关定义见[任务模型文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/001-domain.md)。

比如，评论里只是有人提到“这个按钮有点怪”，是否要自动开工，要看团队设定的规则。已经接手的任务收到后续消息，则还有继续处理的路径，并非每次都创建新工单。

![新任务的简化路径：收到消息，判断是否接单，建立工单，执行，交回结果或请求帮助](/media/d1b375ad6ff555890658006da4d5942c0b428ec02981c4f05361ce9176ada58d.webp)

## 工作做到哪一步，得有个说法

被接下来的工单会分到自己的 agent 会话和工作目录。项目允许配置准备命令，例如用 git worktree 创建一份独立的代码工作区。[执行文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/003-execution.md) 也解释了排队、执行、等待回复、等待检查等状态。

“独立目录”可以想成单独一张工作桌，便于分开放东西。它本身不等于隔离整个操作系统：文档说明，执行会话按运行者的系统身份执行命令。这一点决定了实际部署时应当给它什么环境。

我更感兴趣的是等待状态。一个任务暂时没继续，可能因为还没轮到它，也可能因为它在等人补充信息。两种情况在界面上应当有不同的提示，不然使用者只能反复问“你还在吗”。

做完代码之后，也可以报告“等待检查”。如果交付的是 pull request，也就是一份请求合并的代码改动，使用者还能查看修改内容，再决定怎么处理。

## 源码里，谁负责接单，谁负责干活

这次我先看了两个入口，再对照[架构说明](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/007-architecture.md) 往外找。

* `src/app/runtime.ts` 把存储、消息来源、执行器等部件组装起来，也处理启动和关闭。可以把它看成开门营业前的准备工作。
* `src/core/engine.ts` 集中处理核心状态变化。它再把消息接收、评估、工单、分配和回复交给内部部件。读这个文件，比较容易看出一张工单会经过哪些操作。
* `src/sources/` 连接消息来源；`src/executor/` 接上真正执行工作的会话。这样，接收消息的代码和干活的代码就有了各自的位置。

还有一个小细节：核心状态的修改集中在事务里进行，可以把事务理解成“一组相关修改一起保存”。耗时的外部工作则交给外围部件处理。这有助于避免工单只改了一半，系统就去发消息或启动任务。

## 最想借鉴的是少打扰

项目的[设计原则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/000-philosophy.md) 很在意人要付出多少注意力。接到任务就连续播报十几条进度，未必比安静做完更有帮助；真正需要人决定的事，又不能埋在一堆日志里。

这也给了我一个看 agent 项目的角度：除了它能生成什么，还可以看它怎样安排等待，怎样保存没做完的事情，怎样把结果交回去。

## 它先拆代码，再组图

graphify 有一层 python 实现。负责结构提取的代码会使用 tree-sitter 解析源文件。这个工具做的事情，有点像给句子划分主语、谓语：它先认出程序里的函数、调用、导入等结构，再让后续代码从这些结构里提取关系。[提取入口在 `graphify/extract.py`](https://github.com/graphify-labs/graphify/blob/v8/graphify/extract.py)。

拆出来的结果主要分成两部分：节点，以及节点之间的连线。接着，`build.py` 把它们组装成图，后面还可以做分组、分析和导出。

第一次读源码，我会按这个顺序走：

| 文件                      | 它负责的工作        |
| ----------------------- | ------------- |
| `detect.py`             | 看一遍目录，整理有哪些文件 |
| `extract.py`            | 从文件里提取结构和关系   |
| `build.py`              | 把节点、连线组装起来    |
| `cluster.py`            | 将联系较密切的节点分组   |
| `report.py`、`export.py` | 输出报告和图数据等结果   |

这条路线来自仓库的[架构说明](https://github.com/graphify-labs/graphify/blob/v8/architecture.md)。实际代码已经包含不少语言适配和细节处理，不必为了理解主流程，一开始就跟进每种语言的规则。

代码结构可以用规则提取；文档等材料还可以经过可选的语义分析。两种来源的结果，后续需要一起整理。`build.py` 里就能看到对来源、节点身份和重复数据的处理。[这里可以看组图代码](https://github.com/graphify-labs/graphify/blob/v8/graphify/build.py)。

## 我喜欢它把“不确定”也写出来

架构文档里有三种关系标记，意思分别是：直接提取出来的、有依据的推测、仍然不明确的。

这个区别很有用。程序运行时可能根据条件选择不同函数，也可能临时加载别的模块。光读文件，不一定能把实际执行路线完全确定下来。图画得再漂亮，也不能自动补上这些缺失的信息。

比如，地图上标了一条小路。它是实地测过的，还是根据两栋建筑的位置猜出来的，走之前最好知道。读代码关系图也是这样：对于推测出来的边，还需要回到源文件或运行结果里确认。

## 我会用它回答哪种问题

比起让 ai “把整个项目讲一遍”，我更愿意先问：“保存任务这个操作，会经过哪些地方？”

问题小一点，图里的路线就有了用途，也更容易逐处核对。等这条路线看明白，再看登录、搜索或其他功能。

graphify 值得我继续读的地方，就在这张地图是怎么一步步画出来的。阅读一个大仓库时，能先找到下一处值得看的文件，已经省下不少绕路的时间。

第一屏放名字，接着展示两个功能，最后留一个地址。画面不复杂，但打开视频编辑器后，还是要处理文字、位置、转场和时间轴。

hyperframes 提供了另一条制作路线：先把画面写成网页，再输出视频。[项目说明](https://github.com/heygen-com/hyperframes#readme) 把 html、css、媒体素材和可定位时间的动画作为输入。html 负责放内容，css 决定样子，动画安排它们何时出现、怎样移动。

ai 编程工具可以帮忙写这些文件，hyperframes 则把编排好的画面渲染出来。这样，想改标题里的一个字，就有了一个具体的位置可以改。

## 最关键的是能停在指定的一刻

网页能动，为什么还需要一个专门的项目把它变成视频？

因为制作视频时，需要知道每一帧该长什么样。

假设视频每秒 30 帧，一段 10 秒的画面就有 300 帧。第 0 帧看 0 秒时的状态，第 1 帧看大约 0.033 秒时的状态，后面依次继续。这只是方便理解的帧数例子。

如果动画只能从头播放，然后靠等待时间截图，机器偶尔卡一下，截图就可能错过原本想要的时刻。更方便的办法是能直接告诉画面：“现在显示第 3 秒。”

hyperframes 的渲染引擎围绕这种 seek 能力工作。seek 可以理解成拖动播放器进度条，直接去指定时间。符合约定的网页把这种能力暴露出来，引擎就能逐帧定位和捕获。[引擎说明](https://github.com/heygen-com/hyperframes/blob/main/packages/engine/readme.md) 介绍了这个过程。

## 帧是怎样变成文件的

引擎用 puppeteer 驱动 chrome。puppeteer 是控制浏览器的程序工具；浏览器在后台把网页画出来，不需要人在屏幕前逐次点击。

拿到画面之后，ffmpeg 负责视频编码等工作。可以把它理解成处理音视频的工具箱。更上层的 producer 把捕获、编码、音频混合组织成一条完整流程。[producer 的说明](https://github.com/heygen-com/hyperframes/blob/main/packages/producer/readme.md) 提供了这一层的接口。

![hyperframes 的制作路径：编排网页画面，定位时间，捕获帧，再编码并混合音频](/media/543768e33e9ab23451b9f5f5f075cc46c72e086ebd6ba94508dad04d34c4b5f3.webp)

这张图只画主干。真实项目还需要处理字体、素材加载、视频片段、失败清理等情况。顺着 [`framecapture.ts`](https://github.com/heygen-com/hyperframes/blob/main/packages/engine/src/services/framecapture.ts) 的导入和捕获逻辑看，就能发现这些工作并没有因为“用网页写”而消失。

hyperframes 把主要功能放在 `packages/` 下面，初看可以先认这几个名字：

| 包                 | 大致用途                   |
| ----------------- | ---------------------- |
| `core`            | 共用的定义、解析、运行时和动画适配等基础能力 |
| `engine`          | 控制浏览器，定位时间并取得画面        |
| `producer`        | 安排完整的渲染任务，把各个步骤串起来     |

如果只想知道“文件怎么变视频”，先看 `engine` 和 `producer` 就够了。界面如何编辑画面，可以留到下一轮。完整包清单在[仓库 packages 一节](https://github.com/heygen-com/hyperframes#packages)。

21:T13df,rea 是怎么拆开一个软件的？ 没有源码，ai 凭什么知道软件内部发生了什么？从工具、请求和证据看起。 技术 ai 项目笔记 软件用久了，偶尔会冒出一个念头：这个功能到底是怎么做的？

比如，一款老游戏里，小球往屏幕左边跑，声音也跟着偏到左耳。效果不复杂，可要是没有源码，从哪里找出负责这件事的那几行程序？

rea 想帮人缩短这段摸索的路。它的全名是 reverse engineer anything，中文经常被叫作“逆向一切”。名字挺大，我读这个项目时更关心一个小问题：**ai 到底凭什么知道软件内部发生了什么？**

## 先给 ai 一套能用的工具

一段程序交给计算机执行之前，可能会被编译、压缩、打包。原来清楚的函数名字和注释，有些已经丢了。逆向分析就是从留下来的东西出发，试着还原程序的结构和行为。

这里有个容易误会的地方：反编译出来的代码，通常是帮助人理解逻辑的近似表达。原作者的注释、命名习惯，以及当时为什么这样写，并不会一起回来。

rea 接入了 ghidra、hopper、ida 等已有的分析工具。这些工具负责查看程序里的函数、字符串和调用关系。ai 根据拿到的结果继续提问：这个函数被谁调用？某段文字从哪里出现？相关的计算又发生在哪一处？javascript、electron 等目标还有各自的分析路径。[项目 readme](https://github.com/morluto/rea#readme) 对这些能力做了区分。

可以把这个过程想成检查一台老收音机：分析工具负责测量，ai 负责安排接下来查哪里。每测一次，才多知道一点。

两边通过 mcp 接起来。这个缩写在这里先不用深究，可以把它理解成一套约定好的工具接口：ai 按规定发出请求，rea 返回规定格式的结果。

![rea 分析过程：提出问题，调用分析工具，返回证据，再决定是否继续调查](/media/0e8c2be04e185326b64862767e67c3cd53d09eb2f90888559c5e237dc2c2869c.webp)

图中省略了不同软件格式的具体处理，只保留“提问—取证—再提问”这条主线。

## 结果里为什么还要留一份证据

读 rea 的接口说明时，我比较在意它如何保存结果。

它会为分析结果保留证据记录，记录里有整理后的结果、证据标识，以及存在时的工具原始输出。后续分析可以引用之前的记录。大结果也可以先读摘要，再按需取详情。[mcp 接口说明](https://github.com/morluto/rea/blob/main/docs/reference/mcp-contracts.md) 写了这些字段怎样传递。

这件事有点像做阅读笔记时记下页码。只写“作者认为这样更快”，过两天就很难回头核对；记下出处，就能检查自己有没有理解偏。

放到逆向分析里也是一样。ai 说“这里似乎在调整音量”，最好能指回某个函数或某次分析结果。否则，一段听起来完整的解释，很可能只是把几个零散线索串得太顺了。

## 打开仓库后，可以先看这几处

这个项目已经不小，第一次读没必要把所有目录都翻完。我会先沿着一条请求经过的地方看。

| 位置                                    | 先把它理解成什么                            |
| ------------------------------------- | ----------------------------------- |
| `scripts/rea.mjs`                     | 分路口：判断这次运行的是命令行任务，还是给 ai 使用的 mcp 服务 |
| `src/cli/`、`src/server/`              | 两种入口，把外面的请求转成内部能处理的操作               |
| `src/application/`                    | 组织一次分析要做的事情，供不同入口复用                 |
| `src/ghidra/`、`src/hopper/`、`bridge/` | 接上具体分析工具的地方                         |

上面是阅读路线，不是完整目录清单。入口脚本里的分支能直接看到两种运行方式；更细的模块关系可以对照仓库自带的[架构图](https://github.com/morluto/rea/blob/main/docs/architecture/architecture.mermaid)。

我觉得这套拆法值得学：外部工具各有各的脾气，先把差异放在连接处处理，上层就不用每次都从头适应。
