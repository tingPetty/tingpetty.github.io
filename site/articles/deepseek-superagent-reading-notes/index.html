给 AI 派一件活，它接下来怎么办？

2026.11.144 分钟阅读

一条留言变成工单以后，系统还得安排工作、处理等待，再把结果交回来。

假设你维护着一个小网站，有人留言：“手机上菜单打不开，能修一下吗？”

把这句话交给 AI，让它写一段修复代码，已经不算稀奇。麻烦的是后半程：它要去哪个项目改？中途收到补充说明怎么办？修完了去哪里告诉你？如果卡住了，总不能一直安静地挂着。

DeepSeek 的 dsh-superagent-prototype 把这些事情放到了一起。它面向一个 GitHub 仓库接收任务，也可以接入飞书，安排 Agent 工作，再回到原来的对话里交付结果。

先说清楚范围：仓库首页 把它标为研究原型，并说明公开代码和团队内部版本、设计文章并不完全一样。下面读的是这个公开原型。

一条留言，先变成一张工单

在这个系统里，外部消息进来后，会被记录成事件。系统根据规则判断它是否要求开始一项工作。接下来的解释，先只看“收到一个新任务”这条路径。

通过判断后，系统建立一张 Ticket。这个词可以直接理解成工单：这件事要做什么、为什么可以做、结果回到哪里，都需要有地方记下来。

其中还有一个叫 Mandate 的记录，用来保存这次工作的授权依据和范围。这里不用背英文，记住一个区别就够了：知道有人说了什么，和获准替他做什么，是两件不同的事。 相关定义见任务模型文档。

比如，评论里只是有人提到“这个按钮有点怪”，是否要自动开工，要看团队设定的规则。已经接手的任务收到后续消息，则还有继续处理的路径，并非每次都创建新工单。

工作做到哪一步，得有个说法

被接下来的工单会分到自己的 Agent 会话和工作目录。项目允许配置准备命令，例如用 Git worktree 创建一份独立的代码工作区。执行文档 也解释了排队、执行、等待回复、等待检查等状态。

“独立目录”可以想成单独一张工作桌，便于分开放东西。它本身不等于隔离整个操作系统：文档说明，执行会话按运行者的系统身份执行命令。这一点决定了实际部署时应当给它什么环境。

我更感兴趣的是等待状态。一个任务暂时没继续，可能因为还没轮到它，也可能因为它在等人补充信息。两种情况在界面上应当有不同的提示，不然使用者只能反复问“你还在吗”。

做完代码之后，也可以报告“等待检查”。如果交付的是 Pull Request，也就是一份请求合并的代码改动，使用者还能查看修改内容，再决定怎么处理。

源码里，谁负责接单，谁负责干活

这次我先看了两个入口，再对照架构说明 往外找。

  • src/app/runtime.ts 把存储、消息来源、执行器等部件组装起来，也处理启动和关闭。可以把它看成开门营业前的准备工作。
  • src/core/engine.ts 集中处理核心状态变化。它再把消息接收、评估、工单、分配和回复交给内部部件。读这个文件，比较容易看出一张工单会经过哪些操作。
  • src/sources/ 连接消息来源；src/executor/ 接上真正执行工作的会话。这样，接收消息的代码和干活的代码就有了各自的位置。

还有一个小细节：核心状态的修改集中在事务里进行，可以把事务理解成“一组相关修改一起保存”。耗时的外部工作则交给外围部件处理。这有助于避免工单只改了一半，系统就去发消息或启动任务。

最想借鉴的是少打扰

项目的设计原则 很在意人要付出多少注意力。接到任务就连续播报十几条进度，未必比安静做完更有帮助；真正需要人决定的事，又不能埋在一堆日志里。

这也给了我一个看 Agent 项目的角度：除了它能生成什么，还可以看它怎样安排等待，怎样保存没做完的事情，怎样把结果交回去。

以后读到“全自动干活”这类介绍，我会先去找这几个地方。它们往往决定了这个工具能不能放进日常工作里。
